**Goal:** 为 CFO 构建可在 30 秒内理解的 GPU 预算决策看板，展示支出、具体削减建议和误判成本，并支持 SRE 追溯到原始证据。

**Tech Stack:** 建议 Python / FastAPI / pandas / PyArrow，React / TypeScript / Vite，Docker Compose，官方 FastMCP 工具。依赖版本在实现阶段依据仓库锁定文件和实际安装结果确定。

**Spec:** `track-2/README.md`；`track-2/docs/traps.md`、`data.md`、`rules.md`、`api.md`、`submission.md`；`track-2/starter/claims.schema.json`。补充设计依据为本任务前一轮分析。

## 阶段 3：调查并形成可执行建议（P0）

**产出：** 至少两项经过实际调查的行动候选及透明排序；证据不足的候选允许保留为待试点。

- [ ] 调查成功但全程没有 GPU 计算的工作，估计迁移到 CPU 的候选容量，说明 CPU 成本及性能验证条件。
- [ ] 调查长期低活动交互会话与延迟取消，比较提醒、宽限期和回收策略；不把整段运行时长直接当作节省。
- [ ] 对有证据的节点异常核查同窗口用户、作业阵列及跨节点对照，区分硬件、代码、工作负载差异与无法判断。
- [ ] 用官方 findings、rules 和 causal 校验 Layer B 的建议，记录接受、修正或拒绝的理由。
- [ ] 为每项建议填写行动、责任角色、影响范围、GPU-hours/美元区间、假设、依据、投入和试点条件。
- [ ] 按有依据的保守收益、误判代价、实施难度形成排序；责任角色不冒充真实组织中的已指定负责人。

**验收：** 建议具体到可执行动作；不按 severity 或 finding 数量替代收益排名。无法完成可靠归因时，不给出停用机器的确定建议。

## 阶段 4：量化误判成本（P0）

**产出：** 每项建议都具有收益、误判损失、试点边界和回滚条件。

- [ ] 区分采取错误行动的损失，以及没有采取必要行动的损失。
- [ ] 节点情景显示停用节点数 × 每节点 GPU 数 × 时长带来的名义容量损失，并单列实际排队/需求的不确定性。
- [ ] 回收会话情景展示可能中断的有效工作、重跑和等待影响；没有 checkpoint 信息时使用明确情景区间。
- [ ] CPU 迁移情景列出新增 CPU 成本、可能延迟与需要验证的性能条件。
- [ ] 区分情景区间与统计区间；不把接口固定 confidence 当作经过验证的概率。
- [ ] 为试点设置可观察的成功与停止指标，例如任务完成耗时、队列尾延迟和重跑情况，并说明静态样本不能证明干预效果。

**验收：** 调整停用范围、时长或价格时，收益与风险联动且单位一致。无依据的风险显示未知或情景假设，不显示为零。

- [ ] 实现三张核心卡：支出分布、排序后的行动建议、与所选建议关联的误判成本。
- [ ] 将价格、候选行动组合和风险情景连接到同一分析结果，避免前端另算一套金额。
- [ ] 打通业务金额 → 建议 → findings/根因 → 作业/GPU 明细 → 计算方法的点击路径。
- [ ] 显示样本范围、合成事件标记、情景假设、缺失证据和加载失败状态。
- [ ] 若加入 LLM 解读，只允许引用已获取证据并保留工具调用/token 使用记录；模型或密钥不可用时，看板和确定性分析仍能运行。

**验收：** CFO 可在 30 秒内识别建议与代价；SRE 可以点击复核关键数字；MCP 调用真实可审计。自由聊天不作为首版交付前提。
